What a DiffGRM recommendation looks like while it is being decoded

A first look inside the reveal steps of the masked-diffusion recommender, ahead of the patching experiments. Industrial_and_Scientific, next-item models, 6,297 test users, of 20 checkpoints. Intervals are 95% paired user-bootstrap intervals (2,000 draws) and exclude training-seed variance: there is one checkpoint per configuration.

Summary

We recorded every decode step by step. This is an observational record: nothing in the model was changed, and no patching experiment has been run yet. The record tells us what those experiments should target.

    the question

    Patching the predicted noise, in a model that predicts no noise

    The plan was to take the noise a diffusion model predicts at step t in one run and put it into another run at the same step. DiffGRM cannot be patched that way. It is masked diffusion: it predicts codes, and it has no noise, no schedule and no step input.

    1. Same state, other history

    step 1step 2 · other historystep 3step 4

    Score chosen steps with a second history, on the decode's own partial SID. This is the direct counterpart of the original plan, and it works under beam search.

    2. Other run's own state

    48???

    The second run decoded freely, so its states differ. Taking its prediction then means taking the digit it wrote and letting the first run continue from there.

    3. Inside one step

    Replace one run's activations with another's: an encoder state for one history item, or the decoder's stream after one block at one digit.

    Each of the three needs to know what the unpatched decode does at every step. No such record existed, so we made it first. It is what this page reports.

    Three decodes, step by step

    Each row is one state of the best path of the first-ranked SID at beam 256. They are the first users in cohort order that fit each description, chosen to show the mechanics and not to be typical. In all three the target has the same SID as the user's most recent history item.

    coverage and checks

    Four checkpoints are not in these numbers

    In each of the four, one or two users of 6,297 have a tie broken differently. No target changes rank and Hit@10 is identical. We propose to accept a checkpoint when every differing list is such a tie, to record the count, and to rerun these four.

    Next experiments

    The code for all three kinds of patching is written and tested on a model with random weights: an intervention that changes nothing leaves the output identical, and one that cannot take effect raises an error. None has been run on a trained checkpoint.

    next

    Switch the history at single steps

    Decode with a second history at chosen steps: the same history with its most recent item replaced. This measures at which step the copy of the recent item is committed, and whether later steps can undo an early commit. Protocol to be written before the first switched decode.
